## 问题组 1：策略组解包展开叶节点（Unpack / Flatten Leaf Nodes）的业务语义定义

### 背景与代码事实
- 用户已明确指示：“直接将其他策略组作为节点引用”（Direct Group Reference）与“解包获得其中节点”（Unpack / Flatten Leaf Nodes）均为系统核心特性。
- 实机代码审查表明：Mihomo 已支持直接组引用；但**解包获得叶节点功能在 Go 后端目前完全未实现**（`AllNodeLogicalIDs` 仅为 DAG 空组检测与元数据计数，未参与成员展开）。
- **既有准入边界声明**：未激活节点（`active=false`）、未启用订阅作用域（`NodeScopeEnabledSubscriptions`）与风险拦截节点已被系统准入契约严格剔除，展开能力完全基于已准入节点集合展开，严禁突破或绕过既有准入防线。
- **循环依赖保护基线**：子组展开遇到循环依赖（环路）时，系统严格执行 Fail-Closed 阻断报错并保留展开路径，杜绝死循环与静默丢弃。

### 请用户决策以下业务选项（无预设默认值）
- **子问题 1.1：重复叶节点去重规则与出现顺序 (Deduplication & Ordering)**
  - 当解包多个子组后包含相同的底层有效节点时：
    - **选项 1.1-A (首次出现去重)**：按展开路径首次遍历到的拓扑位置保留单一节点，后续重复出现的节点自动剔除。
    - **选项 1.1-B (允许并存)**：不执行去重，忠实按照展开路径完整列出（供客户端按轮询权重使用）。
- **子问题 1.2：父策略组 Filter 对解包子树的约束边界 (Parent Filter Propagation)**
  - 父策略组配置的 NodeFilter（如地区/协议筛选）：
    - **选项 1.2-A (仅对最终叶节点执行统一过滤)**：展开得到最底层 Leaf 节点全量集合后，仅对该叶节点集合执行一次性统一筛选，不针对中间子组生成派生视图。
    - **选项 1.2-B (级联约束各级子组)**：各级子组在展开过程中逐级应用父过滤条件，只有各级均满足条件的节点才被展开出来。
- **子问题 1.3：已准入节点在健康探测状态下的过滤约束 (Health Classification in Unpacked Pool)**
  - 对于已通过准入（`active=true` 且未被风险剔除）的节点，在父策略组显式配置健康筛选（如仅 healthy）时的展开策略：
    - **选项 1.3-A (严格依据父筛选过滤，不默认剔除 undetermined)**：仅展开符合父策略组显式健康断言的节点；未配置显式健康限制时，healthy、degraded 与 undetermined（未决/尚未探测）均正常展开，仅排除显式 unhealthy 故障节点。
    - **选项 1.3-B (仅展开健康确认节点)**：父策略组无论是否显式配置健康要求，解包展开时均严格要求健康证据为 healthy，未决（undetermined）与降级（degraded）节点均不注入最终列表。

## 问题组 2：策略组成员（显式节点 vs 子策略组）混合交错相对顺序的业务需求确认

### 背景与代码事实
- 实机代码审查（`internal/resolver/graph.go:140-185`）确认：同类型边按 `Position` 保序；但解析器硬编码先遍历显式节点边、后遍历子策略组边，导致节点与子组间的交错相对顺序丢失。**这是已知的解析器实现缺陷，不能将此 bug 包装为等价推荐方案，亦非数据恢复范畴**。

### 请用户决策以下业务选项（无预设默认值）
- 用户在 UI 中编排的“节点与子策略组之间的相对交错顺序”（例如 `[节点A, 子策略组B, 节点C]`）在实际分流业务场景中是否具有确定性的优先级业务意义？
  - **选项 2-A (具有明确业务意义，需交错保序)**：重构图解析器，废除按类型分批遍历，严格按用户指定的全局单一 `Position` 绝对序号进行保序输出。
  - **选项 2-B (无交错业务意义，接受类型分组)**：明确交错顺序在实际分流中无独立业务差异，正式确立“节点在前、子组在后”的规范定义，并在前端 UI 上按类型分块呈现。

## 问题组 3：历史遗留策略组与 `group_nodes` 迁移数据的业务恢复范围与确认

### 背景与代码事实
- 历史 SQLite 库中存在 3 个轮询策略组（`轮询(日本)`、`轮询(新加坡)`、`轮询(包含香港)`），因历史迁移未转换 `include_group_nodes_ids` 且类型为 `load-balance`，当前在库中 live edges 为 0。
- 此外历史冷归档中明确记录了部分便宜节点（Cheap Nodes）的引用关系。
- **严正声明**：严禁使用名称正则过滤器（Name Filter）或 `empty_fallback_pass` 冒充旧 `group_nodes` 的恢复方案。

### 请用户决策以下业务选项（无预设默认值）
- **子问题 3.1：恢复 3 个轮询策略组是否包含便宜节点 (Inclusion of Cheap Nodes)**
  - **选项 3.1-A (包含便宜节点追加)**：历史恢复范围限定为 3 个已审计轮询策略组，并包含历史冷归档中明确记录的便宜节点引用追加。
  - **选项 3.1-B (仅恢复 3 个轮询组，不追加便宜节点)**：历史恢复范围仅限 3 个已审计轮询组，不包含便宜节点的额外追加。
- **子问题 3.2：恢复执行时机与确认路径 (Recovery Timing & Confirmation Path)**
  - **选项 3.2-A (展开能力实现后另行确认恢复)**：待问题组 1 解包展开叶节点能力正式交付上线后，严格按照已核验的历史原配置转换导入，并由管理员另行单独确认生效（不提供立即普通边填充替代方案，确保动态展开语义完整）。
  - **选项 3.2-B (保留归档，自行重配)**：保留历史归档数据，不执行历史自动修补，由管理员在控制台 UI 中自行重新配置绑定成员。

## 问题组 4：非 Mihomo 纯节点导出目标遇到空策略组校验的一致性边界

### 背景与代码事实
- Sing-box / Surge / Quantumult X 为纯节点导出协议，本身不导出任何策略组或分流规则。
- 但实机代码中编译器顶层 `validate()` 目前无条件对所有目标检查策略组：若存在配置了 `UsesEmptyPass` 的空组，立即报错拦截。

### 请用户决策以下业务选项（无预设默认值）
- **选项 4-A (纯节点目标完全忽略策略组校验)**：对于纯节点导出目标，只要有效准入节点数大于 0，编译器跳过对策略组（包括 empty-group 校验）的检查，直接输出纯节点配置。
- **选项 4-B (严格全系统一致性门禁)**：只要配置中存在未决的空策略组，即使请求的是纯节点客户端，也必须强校验拦截并报错，杜绝配置不完整时导出。

## 问题组 5：订阅抓取在完全成功 (Success) 与部分成功 (Partial) 时新节点缺失的分别处理策略

### 背景与代码事实
- 用户已确认抓取完全失败（Failure）时资产 100% 保全。
- 但在刷新结果为完全成功（Success）或部分成功（Partial）时，系统目前执行 `DELETE FROM node_sources` 差集修剪。若某节点被修剪后失去所属的已启用订阅，由于系统的 `NodeScopeEnabledSubscriptions` 作用域机制，该节点将在活动查询与导出中被隐藏（Scope Masking）。
- **特别声明**：本问题仅探讨本地来源修剪边界，不擅自衍生抓取自动重试（Fetch Retry）需求。

### 请用户决策以下业务选项（无预设默认值）
- **子问题 5.1：完全成功 (Success) 时失踪节点是否保留更久的业务处置语义 (Retention vs Differential Pruning)**
  - **选项 5.1-A (即时差集清理业务处置)**：刷新完全成功以上游最新响应为准，立即对上游缺失的失踪节点执行来源差集删除，使本地资产与上游最新快照严格一致，避免保留失效节点。
  - **选项 5.1-B (保留更久业务处置)**：刷新完全成功即便上游未出现旧节点，仍保留旧来源与资产更长时间（例如标记软下线或由用户配置保留缓冲期后再清理），避免因上游瞬时网络或配置调整导致节点立即在作用域中被隐藏。
- **子问题 5.2：部分成功 (Partial，即部分节点解析报错) 时缺失节点策略 (必须单独待决定)**
  - **选项 5.2-A (保守保留旧来源不修剪)**：因本次刷新存在局部报错证据不完备，缺失节点不视同下线，保守保留未见到的旧来源与关联，仅增量追加解析成功的新节点。
  - **选项 5.2-B (以成功提取集差集修剪)**：仅承认本次成功解析出的节点集合，对未在成功集合中出现的旧节点一律执行差集修剪。

## 问题组 6：UI 节点全量分页下的跨页选择（跨页全选/批量操作）作用范围

### 背景与代码事实
- 服务端全 scope 搜索、筛选与分页已经历史冻结为标准架构；当前前端 `NodesView.vue` 本地计算过滤与最多 3 步翻页兜底为已知实现缺口，将统一重构为服务端原生分页联动（本项已定，不提问是否保留本地 3 步翻页）。
- **未确认跨页功能明确原则**：跨页批量选择功能当前属于未确认功能；明确只有在用户明确确认“如果需要（待确定）”时才进入跨页批量全选落地设计；若未获确认，系统默认保持标准单页选择交互，不新增跨页批量作业作用域。

### 请用户决策以下业务选项（无预设默认值）
- **选项 6-A (标准单页选择，未确认不引入跨页全选)**：点击“全选”仅选中当前分页可视的节点（如当前页的 50 或 100 个节点），翻页后重置或累加当前页勾选，批量操作仅作用于当前选中的单页节点集合。
- **选项 6-B (如果需要，待确定支持跨页全局全选)**：如果需要，在全选框旁提供“选择符合当前筛选条件的全部 N 个节点（跨所有分页）”能力，点击后向后端发起跨分页全局批量探测/编辑作业。
