## Decisions

1. 成熟既有 Go tests/SQLite backup/HTTP 客户端/项目运行手册优先。先定向读取 auth/config 文档与受管 secret 路径；合法凭据不可取得时仅暂停身份操作并提供安全审批选项，不能暴破、改鉴权或聊天索取 Token。
2. 工程准备阶段只读生产：核对当前镜像、备份、schema、现有 API 语义与节点分类；写验收工具/恢复计划并在临时 SQLite 与隔离服务中自测。生产写前需 fresh reviewer PASS；因此生产刷新/恢复有依赖，不能与未审查实现一起执行。
3. 验收预算必须源于现有目标：至多选择 3 个现有订阅，每个一次刷新；至多 6 个代表性现有节点，串行或现有低并发探测，一轮总预算 10 分钟。来源：本次治理避免无限扫描的明确验收预算，不作为节点功能普适门禁。保持现有 SSRF/安全解析约束与用户配置；正文包括计数一致性、状态/error 语义、失败不清空节点、导出解析有效性、探针阶段/延迟/真实连接结果一致性。
4. 历史恢复使用当前库、事务日志、可核验前后备份、源关系与历史代码因果；建立 node-id/身份哈希/来源/手动禁用证据/删除证据/失败刷新时间证据分类。仅源仍有效且唯一身份、明确无手动禁用/删除且可证旧 bug 因果者允许恢复。缺 disable/audit 历史就保护不改并报告无法证明的类数量，不能从 960 推导。
5. 幂等恢复工具默认 dry-run；写操作需要精确已审查 allowlist/现态 precondition、立即热备和事务；异常中止不批量放活。旧失败刷新保留原库存的实现不重做，针对发现缺口修复而非退回旧 HEAD。
