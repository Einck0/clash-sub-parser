## Stories
### US1 (P1) Usable target-specific subscriptions
Compatible node targets deliver truly renderable nodes in original order. Mihomo normally preserves full policy/DNS/rules. No option/credential/detour silently discarded.
### US2 (P1) Consistent preview and delivery
Same facts and mode produce the same artifact through direct/live/preview. Successful preview returns a persisted publishable draft; immutable publications are never rewritten.
### US3 (P1) Faithful native plugins
Supported SS plugins/options survive Mihomo rendering; other targets reject unrepresentable plugins rather than downgrade to plain SS.
### US4 (P1) Recover from unusable policy selection
With enabled primary subscription and valid primary nodes, empty-group or selection-exhaustion failure delivers a valid primary-only artifact instead of 422, even when other groups work or normal rules include DIRECT/REJECT. Saved configuration is not modified. Structural corruption, risk/security failures, unsupported protocols/options, chain constraints and system/storage errors remain fail-closed.
### US5 (P1) One applied configuration without loss of independent facts
Each subscription has at most one applied payload/entry generation and one independent raw-original slot, including subscriptions with pins or immutable publication references. Attempts, saved raw and applied membership are distinct facts. Partial success replaces this subscription's membership with only the successfully updated nodes; total failure retains that last applied set and the existing raw without reviving earlier omitted members. Stable node entities, user intent, immutable publication bytes and honest provenance remain independent. Old full connection configurations survive only for verified actual consumers, never indefinitely by refresh count. Physical shrinking requires a separately authorized offline conversion of scratch, never the original database or immutable backup.
### US6 (P1) Operational readiness without repeated full scans
Readiness checks connectivity/schema/required tables without rescanning every historical row; deep integrity remains available through existing maintenance validation. Do not weaken foreign-key enforcement or remove deep integrity diagnostics.

## Requirements
- FR001: Canonical actual renderability underlies strict diagnostics and compatible projection, immutable/order-preserving input, safe reasons, deterministic duplicate handling.
- FR002: Non-Mihomo default compatible; Mihomo strict full policy when valid. Any enabled non-Mihomo chain remains fail-closed; no silent direct downgrade.
- FR003: All-incompatible nonempty candidate inventory remains no_compatible_nodes, not blank success or primary escape. Selection failures are governed by FR007, not catch-all error recovery.
- FR004: Validate explicit modes; shared consistent facts/pipeline; successful preview persists a real draft with accurate manifests/payload refs; no repository retry after facts failure.
- FR005: Native Mihomo SS plugin/options with actual schema validation; no unverified protocol expansion.
- FR006: Preserve stable IDs, source facts, auth/revocation, CAS/revisions, userinfo, ETag, immutable bytes and risk policy. Original iteration had no schema changes; this continuation explicitly authorizes the override-ledger/index migration in FR009. No converter service or compatibility dual tracks.
- FR007: Automatic primary fallback is eligible for empty-group validation or known selection exhaustion (filtered_nodes_empty, empty_routed_group or absent effective Mihomo routing), including partial empty groups and normal builtin routes when export is otherwise failing. A valid builtin-only policy still compiles unchanged. Resolver structural/reference/cycle failures, active chain problems, risk blocked/review/unknown, unsupported node semantics, content/system errors and auth failures do not trigger recovery. Explicit strict mode does not disable this safety recovery for eligible empty-group failures. Primary absent/disabled/no eligible nodes is explicit failure. Fallback uses existing primary-only compiler path, DNS/userinfo, risk reevaluation and chain resolver; never returns raw upstream bytes or edits saved groups/rules. Preserve original failure cause as safe diagnostics along with primary_subscription_fallback.
- FR008: Target contract for storage continuation pi_run_20261110_174812_1075841: a committed subscription has zero or one applied subscription_payloads row, enforced by UNIQUE(subscription_id), and entries only for that generation; no pin/publication/source/version exceptions and no failed synthetic payload. Raw remains in its independent single slot and body_blob in payloads stays empty. Full/partial reconcile replaces payload/entries/current state/membership atomically; partial accepts only this round's successfully updated nodes. Parser input filtered entirely out is an applied empty membership, not a failure which resurrects old members. Existing transport/parse/304 failure semantics and source revision/CAS fences remain; last_attempt, raw and last_applied are not conflated. Fetch summaries retain the latest attempt/applied/raw union, not 100 historical attempts. Pins and publication/origin references move to whitelist-only lightweight evidence preserving original IDs/digests; historical origin never falls back to the latest entry. Provenance quality and original history stay honest; historical raw-name matching anchors survive without keeping parsed JSON. Non-head complete versions may be deleted only after all real consumers are closed and actual leases protect their selected versions in the same transaction; lease expiry alone is not deletion authority. Legacy conversion is an explicit sealed offline scratch operation with verified immutable backup, protected-asset digests, integrity/FK checks and measured capacity including journals. Startup must reject unprepared legacy databases before any migration or cleanup write; new empty databases initialize the same constraint/readiness invariant. These are target requirements, not a claim the partial implementation already meets them.
- FR009: User classification overrides are independent durable intent keyed by subscription + existing override anchor. Migration backfills latest explicit override per anchor deterministically; future set/clear and entry projection occur atomically. Reconcile reads ONLY this ledger for carry-forward (same anchor/name ambiguity rules); do not keep a historical-entry fallback algorithm. Clear removes durable intent. Removing old entries cannot erase an absent node's override, resurrect cleared overrides, or silently change current notice/proxy inventory predicates.
- FR010: Retention is transactional, uses FK/reference checks, reports deleted/protected counts, never deletes subscriptions, nodes, current sources, configurations, node overrides, publication bytes, source-history ledger, audit/risk/probe evidence. Existing retention for probes stays. Those smaller evidence ledgers are explicitly retained this iteration: no indiscriminate time-based deletion without consumer-specific design. Failures roll back cleanup and remain observable without falsely reporting an already committed refresh as failed. Physical VACUUM is not automatic and is not executed on production in this run.
- FR011: /readyz checks live connectivity, schema migration and required tables without full foreign_key_check; full CheckReadiness/integrity remains callable by maintenance/tests. Tests distinguish operational readiness from deep diagnosis and still detect missing schema/tables.
